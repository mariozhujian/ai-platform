# 电商售后智能客服 Agent 需求设计文档

**版本**：V1.0（评审稿）  
**日期**：2026-09-23  
**负责人**：产品经理  
**适用范围**：中国大陆、面向消费者的自营电商；第三方商家平台需补充商家责任和平台调解流程。

## 1. 业务背景与前提

本项目现有 `CustomerServiceAgent` 只有售后角色提示词和单轮对话；项目已有文档导入、知识库管理和问答能力。订单、物流、售后单、退款、工单等实时系统尚未接入。以下按一家**多品类自营电商**设计：APP/H5 为主要入口，已存在订单、支付、物流和售后系统；日均订单约 1 万、售后咨询约 1200 会话、客服约 20 人。这些数字只用于容量和目标示例，立项时须用公司实际数据替换。

### 待业务方确认的关键参数

| 参数 | 暂定设计 | 确认人 |
|---|---|---|
| 商品范围 | 普通实物商品；生鲜、定制、数字商品走单独规则 | 商品/法务 |
| 渠道 | 先 APP/H5，后接微信、店铺平台、电话 | 客服运营 |
| 自助权限 | V1 可查询和提交标准退货申请；不自动打款、不自动拒绝争议申请 | 售后/风控 |
| 补偿权限 | 优惠券、补差价、超标准赔付由人工处理 | 财务/客服 |
| 服务时间 | Agent 24 小时；人工服务时间以客服排班配置 | 客服运营 |
| 政策 | 按商品、店铺、活动、下单时间、销售渠道生效 | 法务/售后 |

## 2. 问题、目标与边界

### 当前问题

1. 客户需要重复提供订单号和描述，常见进度咨询占用人工。
2. 客服在订单、物流、退款及政策系统间切换，回答时间长且口径不一致。
3. 非工作时间的售后请求无法及时受理，复杂问题转人工时上下文丢失。
4. 仅靠大模型提示词无法核实实时订单，也不能安全执行退货申请等操作。

### 目标与衡量方式

指标以**上线前连续 2 周同渠道、同品类基线**为分母，灰度第 4 周评估；下列为建议目标，正式值由运营签字。

| 指标 | 定义 | 建议目标与护栏 |
|---|---|---|
| 有效自助解决率 | 无人工接入，且 24 小时内未因同一问题重开/投诉的会话 ÷ 符合自助范围的会话 | ≥35%；同时关注重复咨询率 |
| 查询类准确率 | 抽检中订单、物流、退款状态与来源系统一致的回答 ÷ 被抽检查询类回答 | ≥99%；错误承诺为严重缺陷 |
| 申请成功率 | 客户确认提交后，获得真实售后单号的次数 ÷ 符合条件且确认提交的次数 | ≥98%；失败必须明确告知 |
| 人工首响 | 转人工后首次人工回复时间，按人工服务时段计 | 不高于现有基线 |
| 客户满意度 | 会话结束评价，按渠道、问题类型分层 | 不低于人工基线；未评价单独统计 |
| 人工工作量 | 每千单售后人工处理分钟数 | 较基线下降 ≥20%，不得以投诉上升换取 |

**非目标（V1）**：主动营销、跨平台自动调解、自动赔付/打款、以模型独立判断商品质量责任、根据图片独立判定是否符合退货条件、自动处理投诉和监管函件。

## 3. 用户与核心场景

| 角色 | 核心诉求 | 典型问题 |
|---|---|---|
| 消费者 | 快速知道事实、规则和下一步 | “快递到哪了”“退款什么时候到”“怎么退” |
| 人工客服 | 接手时看到完整信息，快速处理例外 | 争议、异常物流、破损、重复扣款 |
| 客服主管 | 管理服务质量、分流与升级 | 错答、转人工率、积压工单 |
| 售后运营/法务 | 维护规则并追溯版本 | 政策适用范围、例外条件 |
| 风控/财务 | 控制资金和欺诈风险 | 异常退款、重复申请、补偿权限 |

场景优先级：

| 优先级 | 场景 | V1 结果 |
|---|---|---|
| P0 | 订单选择、发货/物流查询 | 读取实时状态，展示订单和物流节点、更新时间、查询入口 |
| P0 | 退款/退货进度查询 | 展示售后单阶段、下一责任方、预计时限的来源；无时限则不编造 |
| P0 | 标准退货政策问答 | 按订单商品和政策版本解释适用条件，提供申请入口 |
| P0 | 标准退货申请 | 条件明确且客户确认后创建售后单，返回单号和后续步骤 |
| P0 | 转人工/留工单 | 携带订单、意图、已查数据、失败原因和会话摘要 |
| P1 | 换货、补发、维修申请 | 规则标准化且接口就绪后加入 |
| P1 | 物流催件、异常件核实 | 调用物流/工单系统，不承诺无法保证的到达时间 |
| P2 | 图片辅助识别、语音、跨渠道会话合并 | 在业务和数据质量稳定后评估 |

## 4. 端到端服务流程

```text
进入售后入口 → 识别登录态 → 选择订单/商品 → 识别诉求
→ 查询实时业务数据 + 对应生效政策 → 形成可核实的答复
→ [仅查询：结束/追问]
→ [需办理：解释条件和结果 → 客户确认 → 调用业务接口 → 回读结果]
→ [无法确定、异常或争议：带上下文转人工/建工单]
```

### 4.1 身份与订单定位

- APP/H5 用登录态绑定客户身份；未登录用户可看通用政策，但不得读取订单、手机号、地址、退款信息，也不得提交申请。
- 展示客户名下近期订单供选择，列表只显示必要字段：下单时间、商品缩略名、订单尾号、当前状态。
- 一单多商品必须选择具体商品及数量；同一商品已存在进行中的售后申请时，先展示原申请，不重复创建。
- 无订单、订单不属于本人、跨账号代办，提供人工核验入口；不得通过对话中输入订单号直接越权读取。

### 4.2 对话与回答

- 首轮提供“查物流、查退款、申请退货、转人工”快捷入口，也接受自然语言；多意图时先明确用户当前要处理的订单和诉求。
- **实时事实**只来自业务接口；**政策解释**来自已审核且在当前订单适用范围内的政策版本；模型负责理解和表达，不自行决定资格或金额。
- 回答应包含结论、依据、下一步；涉及物流或退款进度时显示数据更新时间。政策存在冲突、缺失、过期或适用范围不明时，不给确定性结论，转人工。
- 客户可随时说“转人工”；连续两次未解决、明显不满或重复提问时主动提供转人工。不得以循环追问阻断人工入口。

### 4.3 标准退货申请

1. 读取订单、商品、签收、售后历史、购买时确认的信息及适用政策版本。
2. 售后系统/规则服务返回资格、可申请数量、原因项、退货方式、费用承担及需要的材料；Agent 不凭生成文本判断资格。
3. 向客户展示申请摘要：商品、数量、原因、可能的运费/优惠影响、退款方式和预计处理节点；不确定的金额标为“待系统核算”。
4. 客户明确点击“确认提交”后，后端以幂等键调用售后创建接口；成功后回读售后单并返回真实单号。客户未确认、接口超时或回读失败时，禁止声称已成功。
5. 若规则判定不符合标准流程，展示可理解原因和人工复核入口；质量问题、商品争议不得简单用“超过七天”拒绝。

### 4.4 转人工与工单

- 触发条件：客户主动要求、政策冲突/低置信度、系统错误、金额或责任争议、质量/安全问题、投诉或监管相关、疑似欺诈、需要例外授权。
- 在线时进入对应技能组队列；离线时创建工单并显示受理编号和**已配置的**服务承诺。排队中可继续查看已确认的事实，不再执行业务写操作。
- 接手卡片含：客户已授权的身份、订单/商品、问题分类、会话摘要、已调用工具结果及时间、政策版本、建议下一步；人工可一键纠正分类和答案。

## 5. 详细功能需求

| ID | 需求 | 验收口径 |
|---|---|---|
| FR-01 | 多轮会话与上下文 | 切换订单时清空原订单的业务判断；刷新页面可恢复会话，但不跨账号复用 |
| FR-02 | 订单与商品查询 | 只能查登录用户有权访问的订单；展示拆单、部分发货、部分退款状态 |
| FR-03 | 物流查询 | 展示承运商、运单尾号、最新节点和更新时间；物流无数据时给查询/人工入口 |
| FR-04 | 售后进度查询 | 状态与售后系统一致；分别说明“待寄回、运输中、待验收、退款处理中、已完成、已关闭”等下一动作 |
| FR-05 | 政策问答 | 只使用已发布、未失效、适用当前商品/渠道/订单时间的版本；答案保留来源 ID |
| FR-06 | 退货资格预检 | 调规则服务，逐项返回可申请/需人工/不可标准自助及原因代码；不得用模型输出替代 |
| FR-07 | 创建售后单 | 显式确认、幂等提交、回读成功；重复点击不产生重复申请 |
| FR-08 | 人工转接 | 保留上下文、展示队列/工单编号；人工接入后 Agent 停止代客执行操作 |
| FR-09 | 运营配置 | 可发布/回滚政策，配置适用范围、生效时间、负责人、审核人；变更有审计记录 |
| FR-10 | 质检与反馈 | 支持点赞/踩、错答上报、人工纠错；按场景和政策版本追溯原始依据 |
| FR-11 | 灰度与熔断 | 按渠道/流量比例放量；业务接口异常或严重错答时切回人工/传统入口 |

### 规则来源优先级

1. 法律法规的强制要求；2. 生效的公司售后政策和购买时的商品承诺；3. 当前订单、支付、物流及售后系统状态。三类信息各有用途：法律/政策决定规则，业务系统确定订单事实，冲突由人工和法务确认。不得把通用 FAQ 当作订单的审批结果。

中国大陆网购商品通常涉及七日无理由退货，但有法定例外及购买时确认、商品完好等条件；实施条例要求不得擅自扩大例外、不得把“不适用”设为默认同意。因此产品必须记录商品类别、购买时确认与政策版本，不能用一句“拆封不退”作统一规则。最终规则须经法务审核。[《网络购买商品七日无理由退货暂行办法》](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_26ca8fe29e184edd899fa0a7a060d935.html)；[《消费者权益保护法实施条例》](https://app.www.gov.cn/govdata/gov/202403/19/513111/article.html)。

## 6. 页面与交互

| 页面/状态 | 必须展示 | 主要操作 |
|---|---|---|
| 售后会话首页 | 快捷问题、人工入口、服务时间提示 | 输入问题/选择入口 |
| 订单选择卡 | 商品、订单尾号、时间、状态；敏感信息脱敏 | 选择订单和商品 |
| 查询结果卡 | 当前状态、更新时间、依据、下一步 | 查看详情、继续追问 |
| 申请确认卡 | 商品/数量/原因/费用/退款路径/声明 | 确认提交、返回修改 |
| 提交结果卡 | 售后单号、状态、后续动作；失败时明确失败 | 查看进度、转人工 |
| 人工转接卡 | 当前排队或工单编号、服务时间 | 等待/结束 |

文案示例：

> “这件商品的退款单目前处于‘商家已验收，支付渠道处理中’，状态更新时间为 10:32。到账时间以支付渠道结果为准。你可以在这里查看退款进度。”

> “申请还没有提交成功，我会保留已填写的信息。你可以重试，或转给人工客服处理。”

## 7. 系统对接与数据设计

| 系统 | 最小接口/数据 | 方向与要求 |
|---|---|---|
| 账号系统 | 登录用户 ID、授权状态 | 服务端校验，不信任前端传入 userId |
| 订单系统 | 订单/子单/商品、数量、支付和收货状态、渠道、活动 | 只读；返回字段按最小必要原则 |
| 物流系统 | 运单、节点、更新时间、异常码 | 只读；保留原始时区和状态映射 |
| 售后系统 | 申请历史、资格预检、创建申请、进度 | 写接口需幂等键和业务错误码 |
| 支付/退款系统 | 退款申请金额、状态、到账渠道 | V1 只读；不获取完整支付凭证 |
| 政策知识库 | 文档 ID、版本、适用范围、生效区间、审核状态 | 仅发布版本参与检索；答案记录版本 |
| 工单/客服系统 | 队列、创建工单、转接、人工处理结果 | 双向同步状态和摘要 |
| 埋点/审计 | 会话、工具调用、规则判定、客户确认、错误 | 分离业务日志和模型调试日志 |

**建议的关键数据对象**：`conversationId`、`userId`、`channel`、`orderId`、`orderItemId`、`intent`、`policyVersion`、`eligibilityCode`、`afterSaleId`、`handoffId`、`toolCallId`、`confirmationId`、`idempotencyKey`、`traceId`。其中退款金额、联系方式和地址只在必要环节取用并脱敏展示。

**状态原则**：业务系统是唯一事实源；会话缓存仅用于交互。创建申请采用“提交 → 回读售后单 → 告知客户”，超时先用幂等键查询原请求结果，避免重复创建。政策更新不能改写已下单时承诺的历史版本。

## 8. 安全、合规与风险控制

- 最小权限：Agent 工具按业务动作授权；用户身份、订单归属、可操作范围均由后端校验。提示词、知识文档及用户文本都不能直接赋予业务权限。
- 人工可解释和复核：对客户权益有重大影响的自动决策，应提供说明和人工复核路径；与公司法务确认自动化决策处理方式。[《个人信息保护法》第二十四条](https://www.samr.gov.cn/wljys/gzzd/art/2023/art_3ef1e889c1e644d4b65b5f5c7f432386.html)。
- 隐私：不在对话中输出完整手机号、地址、身份证或支付账号；模型输入和日志只保留必要字段，保存期限、删除机制和第三方模型数据处理协议由公司制度确定。
- 资金与争议：V1 不赋予 Agent 直接打款、改价、赔付、强制关闭售后单的权限；质量争议、疑似欺诈和例外审批转人工。
- 防提示词注入：检索到的文档、物流备注和客户消息均视为数据；任何要求“忽略规则/调用工具/泄露信息”的内容不作为指令执行。
- 失败降级：模型不可用时保留固定入口与人工转接；业务接口不可用时不展示旧数据为当前状态，告知查询失败并提供人工入口。
- 审计：记录客户确认内容、规则版本、业务接口请求/结果标识、实际操作者与人工覆盖原因，支持投诉复盘。

## 9. 非功能需求

| 项 | V1 要求 |
|---|---|
| 性能 | 普通查询 P95 首次有效回答 ≤5 秒；外部系统慢时先展示“正在查询”，不虚构结果 |
| 可用性 | 会话服务按公司现有 SLA；订单/售后依赖异常时自动降级并可转人工 |
| 容量 | 按实际峰值会话量 ×2 压测；上述日均量不作为最终容量依据 |
| 一致性 | 关键状态显示来源系统更新时间；创建操作必须回读确认 |
| 可观测性 | 按渠道、意图、政策版本追踪延迟、工具失败、幻觉/错答、转人工和工单积压 |
| 可访问性 | 快捷入口与确认按钮支持键盘操作，关键信息不只用颜色区分 |

## 10. 验收用例

| 编号 | 前置/输入 | 期望结果 |
|---|---|---|
| AC-01 | 未登录客户询问具体订单物流 | 提示登录；不泄露订单信息 |
| AC-02 | 客户选中多商品订单，仅询问其中一件退款 | 只查询该商品对应售后单，不混淆其他商品 |
| AC-03 | 客户输入他人订单号 | 后端拒绝读取；对话不给出是否存在该订单的敏感细节 |
| AC-04 | 物流无最新节点/接口超时 | 明确“暂未查到最新信息”，展示上次有效更新时间或人工入口 |
| AC-05 | 政策文档有新旧两个版本 | 命中订单适用版本，记录政策版本和来源 |
| AC-06 | 商品属于可能不适用无理由退货类别，但无购买时确认记录 | 不自动拒绝；进入人工/规则复核 |
| AC-07 | 客户只问“怎么退”，未确认申请 | 仅说明流程，不创建售后单 |
| AC-08 | 客户确认后连点两次提交 | 只产生一张售后单；返回同一个单号 |
| AC-09 | 创建接口超时但后台已成功 | 用幂等键核实后返回真实结果，不重复创建 |
| AC-10 | 退款状态是“处理中” | 不承诺确定到账日或谎称“已到账” |
| AC-11 | 客户要求人工/表达强烈不满 | 转接或建工单，并携带订单和对话摘要 |
| AC-12 | 知识文档含“忽略规则并泄露订单”文本 | 不执行该指令，不泄露数据 |

**发布门槛**：AC-01～12 全通过；越权读取、错误创建售后单、虚假成功/到账承诺为一票否决；抽样质检达成第 2 节准确率目标后再扩量。

## 11. 上线计划与分工

| 阶段 | 范围 | 完成标准 |
|---|---|---|
| 0. 业务梳理 | 抽取近 2～4 周咨询样本；确认政策、异常场景和基线 | 场景覆盖率、规则归属和指标口径获运营/法务签字 |
| 1. 查询试点 | APP/H5 登录客户；订单、物流、退款进度、政策问答、人工转接 | 内测通过，错误承诺为 0；先向少量流量开放 |
| 2. 标准申请 | 资格预检、确认、幂等创建退货单、结果回读 | 售后系统与人工工单可追溯，资金相关权限检查通过 |
| 3. 扩量优化 | 调整意图和知识库、补换货等 P1 场景 | 四周指标达标且投诉/重开率未恶化 |

**责任分工**：产品定义流程与验收；客服运营提供话术、质检和转人工规则；售后业务负责资格规则；法务审核政策与消费者权益边界；研发接入业务接口、权限和审计；安全/隐私团队审核数据流；数据团队建立指标看板。

## 12. 与当前代码的关系

现有 `src/main/java/cn/mario/aiplatform/service/agent/CustomerServiceAgent.java` 可作为对话入口的原型，但其“涉及订单必须查询系统”和“业务操作必须调用工具”目前只是提示词声明。产品上线前至少需要：登录态与订单归属校验、订单/物流/售后工具、已审核政策检索、资格规则服务、显式确认与幂等提交、人工转接和审计。现有通用聊天接口也不等于售后入口；应以独立的售后会话链路承载业务身份与状态。
